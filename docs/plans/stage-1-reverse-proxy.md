# План — Этап 1: базовый reverse proxy + round-robin

Ветка: `stage-1-reverse-proxy` (уже создана от `master`, изменений нет).
Исполнитель плана: модель Fable. Формат плана — «цель, границы, инварианты,
критерий готовности», без построчного кода.

## Цель

Превратить заглушки `internal/proxy` + `cmd/circuitproxy/main.go` в работающий L7
reverse proxy: HTTP-сервер поднимается на `cfg.Listen`, каждый входящий запрос
раскладывается round-robin по статическому пулу backend'ов из конфига и проксируется
через `net/http/httputil.ReverseProxy`. Тело и заголовки проходят корректно в обе
стороны. Всё покрыто тестами под `-race`.

Это первый этап, где приложение реально что-то делает по сети. Ядро проекта
(circuit breaker) — не здесь; здесь простой честный балансировщик, но с корректной
конкурентной моделью round-robin счётчика, потому что дальше на него нарастят breaker.

## Границы этапа — что НЕ делать

Строго только balancer + proxy + сервер. Не реализовывать и не «подготавливать
заранее» соседние этапы:

- **Health-check (Этап 2)** — не писать. Поле `Backend.up atomic.Bool` уже
  зарезервировано под него: **инициализировать его в `true` при создании backend'а,
  но НЕ фильтровать по нему в `Next()` на этом этапе.** Все backend'ы считаются
  живыми. TODO(Этап 2) в `Next()` оставить.
- **Circuit breaker (Этап 3)** — не трогать `internal/breaker`, не звать `Allow`/
  `Report`, не добавлять breaker-поля. TODO(Этап 3) в `Handler()` оставить.
- **Retry / backoff (Этап 4)** — не реализовывать. Один запрос → один backend →
  один проброс. TODO(Этап 4) оставить.
- **Валидация конфига (Этап 5)** — не расширять `config.Load`. Достаточно
  минимальной проверки на входе balancer'а (см. ниже). Схему `config.Config` НЕ
  менять — она общая для всех этапов.
- Не добавлять внешние зависимости — **только stdlib** (`net/http`,
  `net/http/httputil`, `net/url`, `sync/atomic`, `log/slog`, `context`, `os/signal`).
- Не менять существующие сигнатуры так, чтобы разъехалось с заглушками (см.
  «Публичный API» — сигнатуры зафиксированы).

Точки расширения не ломать: комментарии-TODO соседних этапов сохранить, поле `up`
не удалять, слоёную зависимость `proxy → config` не инвертировать.

## Публичный API (зафиксирован — не менять сигнатуры)

Эти сигнатуры уже есть в заглушке `internal/proxy/proxy.go` и на них завязаны
будущие этапы. Реализовать их тело, сигнатуры оставить как есть:

```go
type Backend struct {
    URL *url.URL
    up  atomic.Bool   // Этап 2; на Этапе 1 просто инициализировать в true
}

type Balancer struct {
    backends []*Backend
    counter  atomic.Uint64
}

func NewBalancer(cfg *config.Config) (*Balancer, error)
func (b *Balancer) Next() *Backend
func (b *Balancer) Handler() http.Handler
```

Допустимо добавить неэкспортируемые поля/хелперы в `Balancer` или новые
неэкспортируемые функции, если это упрощает реализацию и тесты. Экспортируемую
поверхность выше — не расширять и не сужать без необходимости.

### Ответственность каждого метода

- **`NewBalancer(cfg)`** — распарсить `cfg.Backends` (`[]string`) в `[]*Backend`
  через `url.Parse`. Каждому backend'у выставить `up = true`. Вернуть ошибку, если
  список backend'ов пуст или какой-то URL не парсится / не абсолютный (нет scheme
  или host) — это единственная валидация, уместная на этом этапе (balancer без
  backend'ов бессмыслен и `Next()` иначе делил бы на ноль).
- **`Next()`** — вернуть следующий backend round-robin: атомарный инкремент
  `counter` и индекс по модулю `len(backends)`. Потокобезопасно, без мьютексов.
  Если пул пуст — вернуть `nil` (в норме не случается, т.к. `NewBalancer` это
  отсёк, но контракт «nil если некого выбрать» сохранить — на Этапе 2 он станет
  реальным, когда все backend'ы down). На Этапе 1 фильтрации по `up` нет.
- **`Handler()`** — вернуть `http.Handler`, который на каждый запрос: берёт backend
  через `Next()`; если `nil` → отвечает `503 Service Unavailable`; иначе проксирует
  запрос на выбранный backend через `httputil.ReverseProxy`.

## Инварианты (обязательные)

1. **Round-robin через atomic, без мьютексов.** Выбор backend'а — только
   `counter.Add(1)` + модуль. Никаких `sync.Mutex` на пути `Next()`. Это горячий
   путь и он должен быть гоночно-чистым под `-race` при параллельных вызовах.
   (Замечание про равномерность: `Add` возвращает пост-инкремент; чтобы первый
   вызов дал индекс 0, брать `(counter.Add(1) - 1) % n` — конкретную формулу
   выбирает исполнитель, важно лишь: атомарно и равномерно по модулю `n`.)
2. **ReverseProxy на backend, а не на запрос без адреса.** Director/Rewrite должен
   переписывать target на базовый URL выбранного backend'а (scheme + host),
   сохраняя path и query исходного запроса. Использовать `ReverseProxy.Rewrite`
   (Go 1.20+, предпочтительно) либо `Director` — но единообразно. При `Rewrite`
   вызвать `pr.SetURL(target)` и `pr.SetXForwarded()` (или эквивалент), чтобы
   заголовки X-Forwarded-* проставлялись корректно.
3. **Тело и заголовки проксируются прозрачно** в обе стороны (request → backend,
   backend response → client), включая метод, статус-код и тело ответа. Это то,
   что `httputil.ReverseProxy` делает сам — задача не сломать это ручной обвязкой.
4. **Один `*httputil.ReverseProxy` переиспользуется** между запросами (создаётся
   один раз в `Handler()`), а не по одному на запрос — иначе теряется пул
   соединений транспорта. Выбор конкретного backend'а делается в
   `Rewrite`/`Director` на каждый запрос (через `Next()`), а не пересозданием
   proxy. Способ передать выбранный backend в замыкание Rewrite оставляю
   исполнителю (замыкание над balancer'ом — простейший вариант).
5. **Ошибки апстрима не роняют прокси.** Задать `ReverseProxy.ErrorHandler`,
   который при ошибке транспорта (backend недоступен) логирует через `slog` и
   отвечает клиенту `502 Bad Gateway`, а не паникует и не отдаёт пустой ответ.
   (На Этапе 4 сюда встроится retry, на Этапе 3 — breaker; сейчас — просто 502.)

- Построить balancer: `proxy.NewBalancer(cfg)`; при ошибке — вернуть её из `run()`.

- Оставить/адаптировать `slog.Info` про старт (listen, число backend'ов). Убрать

## Обязательные тестовые сценарии

Пакет `internal/proxy`, файл `proxy_test.go`. Backend'ы — `httptest.Server`
(паттерн из SKILL.md), без Docker, всё in-process. Обязательный минимум:

1. **Round-robin распределение.** Поднять 3 `httptest.Server`, каждый отвечает
   уникальным маркером (например, свой индекс в теле/заголовке). Сделать через
   прокси-`Handler` серию из `k * N` запросов (N = число backend'ов). Проверить,
   что каждый backend получил ровно `k` запросов (равномерность round-robin), а
   порядок — циклический. Это прямой критерий «запросы равномерно раскладываются».
2. **Прозрачность тела запроса.** POST с непустым телом → backend видит тот же
   body байт-в-байт.
3. **Прозрачность заголовков запроса.** Кастомный заголовок клиента доходит до
   backend'а; проверить также, что проставлен `X-Forwarded-For` (следствие
   `SetXForwarded`).
4. **Прозрачность ответа.** Backend возвращает нестандартный статус (напр. 201),
   кастомный response-заголовок и тело — клиент получает их без искажений.
5. **`Next()` unit-тест на равномерность/цикличность** отдельно от HTTP: на пуле
   из n backend'ов `Next()` вызванный `m*n` раз возвращает каждый backend по `m`
   раз в правильном порядке.
6. **`Next()` конкурентно (`-race`).** N горутин параллельно дёргают `Next()`
   (ждут общий `start`-канал, стартуют разом, как в SKILL.md); суммарное число
   выборов = числу вызовов, детектор гонок молчит. Проверяем гоночную чистоту
   atomic-счётчика, а не идеальную равномерность (при конкуренции порядок не
   детерминирован — не ассертить строгую равномерность в этом тесте).
7. **`NewBalancer` на плохом входе.** Пустой `Backends` → ошибка; невалидный URL
   (например `"://bad"` или без host) → ошибка. Валидный конфиг → без ошибки и
   `len(backends)` совпадает.
8. **Backend недоступен → 502** (проверка `ErrorHandler`, инвариант 5).
   Поднять `httptest.Server`, взять его URL, затем `Close()` его — запрос через
   прокси возвращает `502`, прокси не падает.

Тестам не полагаться на реальные таймеры/`Sleep`. Один-два `httptest.Server` на
тест достаточно, кроме round-robin теста (там 3).
