## Цель

Два независимых блока в рамках одного этапа:

1. **Валидация конфига.** `config.Load` получает слой валидации схемы с понятными,
   actionable-сообщениями об ошибках: непустой список backend'ов и валидные URL,
   валидный listen-адрес, неотрицательные thresholds/timeouts. Быстрый отказ ДО
   старта сервера.
2. **Наблюдаемость.** Структурное логирование (`log/slog`) переходов состояний
   circuit breaker'а (closed→open, open→half-open, half-open→closed,
   half-open→open) с backend-меткой; счётчики (запросы, ошибки, fast-fail,
   ретраи) через stdlib `expvar`, отдаваемые на **отдельном** listener'е.

DoD (из TECHNICAL_PLAN): конфиг валидируется; переходы breaker'а видны в
логах/метриках.

## Ключевые архитектурные решения (приняты — реализовать как описано)

### Решение 1 — как логировать переходы breaker'а, не трогая конкурентную корректность Этапа 3

**Принято: вариант (a) — synchronous callback `OnTransition` в `breaker.Config`.**
`breaker.Config` получает новое опциональное поле:

```go
// OnTransition, if set, is called synchronously at the exact moment the breaker
// changes state, with the previous and new state. It runs on the goroutine that
// caused the transition, INSIDE Report/Allow, AFTER the atomic state store. It
// must be cheap and non-blocking (no I/O that can stall, no locks that can
// contend on the hot path). Optional; nil disables transition logging.
OnTransition func(from, to State)
```

`proxy.NewBalancer` при конструировании `breaker.New(...)` на каждый backend
передаёт backend-aware замыкание, логирующее через `slog` с меткой
`"backend", backend.URL.String()` (см. Решение 2).

**Почему (a), а не (b) «сравнивать `State()` до/после `Report()` снаружи».**
Вариант (b) — гонка: между внешним «прочитать `State()` до» и «прочитать
`State()` после `Report()`» другая горутина может успеть сделать ещё один
переход. Внешний наблюдатель тогда либо пропустит переход, либо припишет чужой
переход своему запросу, либо залогирует несогласованную пару (from чужого
перехода + to ещё более позднего). Breaker специально хранит состояние в
atomic-полях без внешнего замка ровно для того, чтобы переходы были атомарны;
единственная точка, которая ЗНАЕТ, что переход реально произошёл и какой именно,
— это код внутри `Report()`/`Allow()`, там же, где выполняется atomic-store
нового состояния. Поэтому колбэк живёт там.

**Инвариант «горячий путь closed без переходов не платит ничего».** Колбэк
вызывается **строго при реальной смене состояния**, а не на каждый `Report`.
Конкретно, точки вызова (не менять порядок существующих atomic-операций, только
добавить вызов колбэка в местах, где переход уже фактически совершён):

- **`Report()`, ветка `StateHalfOpen`, success:** после `state.Store(StateClosed)`
  и ДО либо ПОСЛЕ `trialInFlight.Store(false)` — колбэк `(StateHalfOpen,
  StateClosed)`. Порядок «probe slot освобождается ПОСЛЕДНИМ»
  (`breaker.go` строки ~140–143) — **load-bearing, не трогать**: вызов колбэка не
  должен вклиниваться между `state.Store` и `trialInFlight.Store(false)` так,
  чтобы отодвинуть освобождение слота на неопределённое время под чужой I/O. Так
  как колбэк логирует (потенциально не мгновенно), **вызывать его ПОСЛЕ
  `trialInFlight.Store(false)`** — слот к тому моменту уже свободен, инвариант
  «ровно один пробник» сохранён, а колбэк лишь читает уже-совершившийся факт
  перехода. Значения `from`/`to` захватываются как локальные константы перехода
  (half-open→closed), не перечитываются из atomic после освобождения слота
  (иначе — та же гонка, что в варианте (b)).
- **`Report()`, ветка `StateHalfOpen`, failure:** симметрично — после
  `state.Store(StateOpen)` и `trialInFlight.Store(false)` вызвать колбэк
  `(StateHalfOpen, StateOpen)`.
- **`Report()`, ветка `StateClosed`, failure, порог достигнут:** колбэк
  `(StateClosed, StateOpen)` вызывать **только внутри успешного
  `state.CompareAndSwap(StateClosed, StateOpen)`** (строки ~155–157). Именно эта
  ветка — единственное место, где closed→open реально совершается; проигравший CAS
  перехода не делает и колбэк не зовёт. Success-путь в closed (сброс failures) —
  НЕ переход, колбэк не зовётся никогда. Так горячий путь closed без падений
  колбэк не трогает вовсе.
- **`Allow()`, ветка `StateOpen`, таймаут истёк:** переход open→half-open делается
  через `state.CompareAndSwap(StateOpen, StateHalfOpen)` (строка ~108). Колбэк
  `(StateOpen, StateHalfOpen)` вызывать **только когда этот CAS вернул `true`** —
  победитель CAS и есть тот, кто совершил переход; проигравшие видят уже
  half-open и колбэк не зовут (иначе N-кратное дублирование лога одного перехода
  под нагрузкой). Сейчас код игнорирует результат CAS (`b.state.CompareAndSwap(...)`
  без проверки) — исполнителю проверить возвращаемое значение, вызвать колбэк в
  ветке `true`, поведение допуска пробника (`admitHalfOpenProbe`) **не менять**
  (по-прежнему вызывается и победителем, и проигравшими).

**Требования к колбэку (задокументировать комментарием у поля):** синхронный,
дешёвый, неблокирующий; выполняется на горутине запроса внутри критичной секции
переходов; не должен захватывать замки, конкурирующие на горячем пути, и не должен
паниковать (паника прострелит `Report`/`Allow`). Аллокаций на горячем closed-пути
без переходов быть не должно — это выполнено тем, что колбэк зовётся только при
реальном переходе. `slog`-логирование внутри колбэка приемлемо: это переход, он
редкий по определению.

**Сигнатура `(from, to State)` без метки.** Метку backend'а знает `proxy`, не
`breaker`; она вносится через замыкание на стороне `proxy` (Решение 2). Breaker
остаётся не знающим про backend-адреса — слоение пакетов Этапа 0 сохранено.

### Решение 2 — куда подключить breaker'ы к меткам backend'ов

`proxy.NewBalancer` уже конструирует `breaker.New(...)` в цикле по backend'ам
(`proxy.go` строки ~84–91) — это **единственное** место, где известны одновременно
и `breaker.Config`, и `backend.URL`. Там же передать `OnTransition`-замыкание:

```go
b.cb = breaker.New(breaker.Config{
    FailureThreshold: cfg.Breaker.FailureThreshold,
    OpenTimeout:      cfg.Breaker.OpenTimeout(),
    OnTransition: func(from, to breaker.State) {
        slog.Info("circuit breaker transition",
            "backend", b.URL.String(),
            "from", from.String(),
            "to", to.String(),
        )
    },
})
```

- **Не пересматривать**, где живут `Backend`/`Balancer` — Этапы 1–4 их не меняли.
- Замыкание захватывает `b` (конкретный `*Backend`) — убедиться, что захват идёт
  по правильной переменной цикла (в Go 1.22+ переменная цикла на каждой итерации
  своя, но `b` тут — это `b := &Backend{...}`, локальная в теле цикла, так что
  захват корректен; проверить, что не захватывается общий индекс).
- **`State` должен уметь печататься читаемо.** Добавить `func (s State) String()
  string` в `breaker` (closed/open/half-open), чтобы лог был человекочитаемым, а
  не числами `0/1/2`. Это чистое дополнение к breaker API, конкурентную модель не
  трогает.
- Уровень логирования: переход в open/half-open/closed — `slog.Info` (по образцу
  `healthcheck.mark`: `slog.Info("backend recovered", ...)`). Не заводить `Warn`
  для open отдельно без необходимости — держать единообразно `Info` с полями
  from/to; оператор фильтрует по `to=open`. (Исполнитель может выбрать `Warn` для
  перехода в `open` по аналогии с `backend marked down` — это допустимо, но
  зафиксировать выбор комментарием, не оставлять случайным.)

### Решение 3 — метрики: `expvar` на отдельном listener'е

**Принято: `expvar` (stdlib) на ОТДЕЛЬНОМ, опциональном listener'е**, адрес из
нового необязательного конфиг-поля `metrics_listen`. Обоснование по двум осям:

**Почему `expvar`, а не самописный `/metrics`.** `expvar` — чистый stdlib, счётчики
(`expvar.Int`) потокобезопасны (atomic внутри), регистрируются один раз и не
требуют своего форматтера/парсера. Самописный `/metrics` не даёт ничего сверх для
учебного MVP, но добавляет код форматирования. TECHNICAL_PLAN разрешает любой из
двух — выбираем меньший по объёму и полностью stdlib.

**Почему ОТДЕЛЬНЫЙ listener, а не тот же порт.** Основной listener обслуживает
`balancer.Handler()`, который **проксирует ЛЮБОЙ входящий путь** на backend.
Примонтировать `/debug/vars` (или `/metrics`) на тот же `http.ServeMux`/listener
означает, что клиентский запрос с путём `/debug/vars` (или `/metrics`) будет
перехвачен нашим хендлером метрик вместо проксирования — тихая подмена
пользовательского трафика. Реальные reverse-proxy отдают админ/метрики на
отдельном порту ровно поэтому. Для MVP это минимальное корректное решение:
- новое поле конфига `Listen` для метрик — **опциональное**, дефолт «выключено»
  (пустая строка → метрик-сервер не поднимается вовсе, только логи переходов);
- когда поле задано — в `cmd/main.go` поднимается ВТОРОЙ `http.Server` на этом
  адресе с `expvar.Handler()` (или `http.DefaultServeMux`, куда `expvar`
  авто-регистрирует `/debug/vars`), живущий/гасящийся по тому же `ctx` и с той же
  graceful-shutdown-логикой, что основной сервер.

**Держать МИНИМАЛЬНЫМ.** Это не отдельный этап. Не добавлять аутентификацию,
TLS, Prometheus-экспозицию, per-backend разбивку счётчиков сверх DoD. Достаточно
небольшого набора глобальных счётчиков (см. ниже).

**Набор счётчиков (`expvar.Int`, глобальные в пакете `proxy`, публикуются под
понятными именами).** Инкрементировать в естественных точках классификации исхода
в `retryTransport.RoundTrip`/`pickBackend`:
- `requests_total` — входящие запросы (инкремент один раз на `RoundTrip`, в начале).
- `errors_total` — запросы, завершившиеся ошибкой для клиента (финальный исход —
  транспортная ошибка или финальный 5xx; инкремент в точке возврата
  неуспешного результата, ровно один раз на запрос).
- `fast_fail_total` — случаи, когда ни одна попытка не стартовала из-за
  `errNoBackends`/`errAllCircuitsOpen` (fast-fail 503). Инкремент там, где эти
  sentinel'ы возвращаются как финал.
- `retries_total` — число фактически выполненных повторных попыток (инкремент на
  каждой итерации цикла с `attempt > 0`, т.е. каждый реальный retry сверх первой
  попытки).

Точные имена/группировку (плоские `expvar.Int` vs `expvar.Map`) выбирает
исполнитель; требование — счётчики видны на `/debug/vars`, растут в ожидаемых
точках, потокобезопасны (`expvar.Int` уже atomic — дополнительной синхронизации не
нужно). Регистрировать через `expvar.NewInt(...)` в `var (...)`-блоке пакета
(единожды при инициализации); не вызывать `NewInt` с одним именем дважды — паника
дубликата. Если тестам нужен доступ к счётчикам — экспортировать через
`export_test.go` или читать через `expvar.Get(name)`.

**Инкременты — только ДОБАВЛЕНИЕ поверх существующих точек классификации Этапа 4,
без переделки цикла попыток** (граница ниже).

### Решение 4 — граница валидации `config.Load()` vs проверки потребителей

`config.Load` получает **дополнительный ранний слой** валидации (быстрый отказ с
понятным сообщением до старта сервера). Существующие проверки в
`proxy.NewBalancer` (пустой список, невалидный/неабсолютный URL) и
consumer-defaults (`breaker.New`, `healthcheck.New`, `newRetryTransport`)
**остаются как defense-in-depth** — они защищают путь конструирования структур
напрямую в коде/тестах, минуя `Load()`. Сообщения не должны противоречиво
дублироваться для одного инварианта: где смысл совпадает (backend URL), допустимо
осознанное дублирование двух независимых слоёв с одинаковым вердиктом — см. ниже.

**Поля, которые `Load()` обязан провалидировать, и критерий «валидно/невалидно»**
(применяя критерий Этапа 4 «ноль выключает опциональную фичу» vs «ноль/отриц.
ломает инвариант»):

- **`Listen`** — непустая строка, разбирается `net.SplitHostPort` без ошибки, и
  порт — число (или именованный порт? — для MVP требовать числовой порт), host
  может быть пустым (форма `:8080` валидна). Пустая строка `Listen` → ошибка
  «listen address is empty». Неразбираемый адрес → ошибка с указанием значения.
- **`Backends`** — непустой список; каждый элемент парсится `url.Parse` без ошибки
  и абсолютен (`Scheme != "" && Host != ""`). Пустой список → ошибка «no backends
  configured». Невалидный/относительный URL → ошибка с указанием проблемного
  значения.
  - **Дублирование с `NewBalancer`:** `NewBalancer` уже делает ровно эту проверку.
    **Принято: вынести парсинг+валидацию одного backend-URL в общий экспортируемый
    хелпер в пакете `config`** (напр. `config.ParseBackendURL(raw string)
    (*url.URL, error)` или `Config.Validate()` возвращает распарсенные URL), и
    `NewBalancer` использует его же — тогда сообщение об ошибке одно, слои не
    разъезжаются. Если вынос усложняет (циклы импорта — `config` не должен зависеть
    от `proxy`; хелпер живёт в `config`, `proxy` его импортирует — цикла нет),
    предпочесть вынос. Альтернатива (осознанное дублирование двух защитных слоёв с
    одним вердиктом) допустима, но менее желательна — выбрать вынос, если он выходит
    чистым; обосновать выбор комментарием.
- **`HealthCheck.IntervalSeconds` / `TimeoutSeconds`, `Breaker.OpenTimeoutSeconds`**
  — **отрицательное значение → ошибка валидации** с понятным сообщением
  (`"health_check.interval_seconds must not be negative"` и т.п.). **Ноль/omitted
  — валидны** (поле необязательно; потребитель подставит дефолт). То есть `Load()`
  требует `>= 0`, но НЕ требует `> 0`.
  - **Consumer-side дефолты Этапов 2–3 ОСТАЮТСЯ** как fallback на случай
    нуля/omitted (валидный кейс). Они НЕ становятся мёртвым кодом: `Load()`
    пропускает ноль, а `breaker.New`/`healthcheck.New` превращают его в рабочий
    дефолт. Regression-тесты Этапов 2–3 на дефолты остаются зелёными как есть —
    **не удалять и не менять** (они проверяют именно ветку «ноль → дефолт», которую
    валидация сознательно не перехватывает).
- **`Retry.MaxRetries`** — **принято: (i) `Load()` НЕ валидирует `max_retries`
  вообще.** И `0` («ретраи выключены» — осознанный выбор), и отрицательное (мусор,
  тихо нормализуется к 0 в `newRetryTransport`) — не ошибки конфига по устоявшейся
  на Этапе 4 философии «ноль/отрицательное для этого поля тихо нормализуется».
  Валидация смотрит только на ДРУГИЕ поля.
  - Обоснование: TECHNICAL_PLAN говорит «positive thresholds/timeouts», но
    `max_retries` — не threshold и не timeout; это счётчик опциональных попыток,
    для которого проект уже зафиксировал (Этап 4, Решение 4) семантику «ноль
    выключает фичу», а `-1` намеренно ведёт себя как «одна попытка», НЕ как ошибка.
    Ломать это в `Load()` противоречило бы уже принятому и покрытому тестом
    контракту.
  - **Существующий тест `TestRetry_MaxRetriesZeroOrNegativeSingleAttempt`
    (`internal/proxy/retry_test.go`) остаётся как есть, не трогать** — он проверяет
    нормализацию на уровне конструктора `newRetryTransport`, который валиден
    независимо от `Load()` (кто-то может собрать `RetryConfig` в коде). Валидация и
    конструктор-дефолт — разные уровни, противоречия нет.
- **`Retry.BackoffBaseMs`** — по той же логике `Load()` его **не валидирует**
  (нормализация к `defaultBackoffBase` при `MaxRetries>0` живёт в
  `newRetryTransport`, Этап 4). Отрицательный base — теоретически мусор, но
  нормализация потребителя уже его нейтрализует (`<=0 → default`); ранняя ошибка
  тут ничего не спасает и противоречила бы парности с `max_retries`. Оставить как
  есть.
- **`Breaker.FailureThreshold`** — по аналогии с `MaxRetries`: `<=0` уже тихо
  дефолтится к 1 в `breaker.New` (строки ~78–80, комментарий «normalize a
  non-positive threshold to 1»). **Принято: `Load()` НЕ валидирует
  `failure_threshold`** — нормализация к 1 в конструкторе остаётся истиной в
  последней инстанции, ноль/отрицательное = «открывать по первой ошибке», не
  ошибка конфига. Regression-логика конструктора breaker'а не трогается.

**Итог по границе:** `Load()` валидирует `Listen`, `Backends` и знаковость трёх
временных полей (`interval_seconds`, `timeout_seconds`, `open_timeout_seconds` —
отрицательное запрещено, ноль разрешён). Поля retry и `failure_threshold` `Load()`
не трогает — их семантика «ноль/отрицательное осмысленно нормализуется» уже
зафиксирована и покрыта тестами; consumer-defaults остаются рабочим слоем.

### Решение 5 — формат ошибок валидации

**Принято: возвращать ПЕРВУЮ найденную ошибку валидации**, обёрнутую через
`fmt.Errorf("config %q: <что не так>: %w", path, ...)` в стиле существующего
`Load()`. Не заводить агрегирующий тип «собрать все ошибки разом».

Обоснование: для учебного MVP «понятные ошибки» из TECHNICAL_PLAN = сообщение,
однозначно называющее проблемное поле и значение, чтобы оператор мог исправить.
Первой ошибки для этого достаточно; агрегатор всех ошибок — оправданное усложнение
только для больших конфигов с множеством полей, чего тут нет. Сообщения делать
actionable: называть поле (`listen`, `backends[2]`,
`health_check.interval_seconds`), значение и ожидание. Порядок проверок
детерминирован (сначала `Listen`, затем `Backends`, затем временные поля), чтобы
сообщения были предсказуемы для табличного теста.

Форму реализации (валидация прямо в `Load()` после `Unmarshal` vs отдельный
метод `Config.Validate() error`, вызываемый из `Load()`) выбирает исполнитель;
предпочтительнее отдельный `Config.Validate()` — тестируется без файла на диске.

## Границы (что НЕ трогать)

- **Конкурентная модель breaker'а** — `state`/`trialInFlight`/`openedAtNanos` CAS,
  порядок операций в `Report()` (освобождение слота ПОСЛЕДНИМ, строки ~140–143) и
  в `Allow()`. Хук `OnTransition` добавляется **аккуратно поверх**, не меняя
  порядок существующих atomic-операций (Решение 1). Проверка результата CAS в
  `Allow()` (open→half-open) и в `Report()` closed-ветке добавляется для вызова
  колбэка, но НЕ меняет логику допуска пробника.
- **Архитектура ретрая** — `retryTransport` как единственный владелец цикла
  попыток, per-attempt `Next`+`Allow`+`Report`, буферизация тела, backoff+jitter
  (Этап 4). Счётчики `expvar` **добавляются поверх** уже существующих точек
  классификации исхода, без переделки цикла попыток.
- **Архитектура ретрая — тест `TestRetry_MaxRetriesZeroOrNegativeSingleAttempt`**
  и regression-тесты дефолтов Этапов 2–3 (`breaker`/`healthcheck`) — **не удалять,
  не менять** (Решение 4).
- **JSON-теги и структура существующих полей `config.Config`** и
  **`config.example.json`** (существующие секции) — не менять. Валидация — НОВАЯ
  логика поверх существующей схемы, не смена схемы.
- **Новое поле `metrics_listen`** добавляется как опциональное с дефолтом
  «выключено» (пустая строка). Добавить его и в `config.example.json` как пример
  (опционально, с комментарием-соседним значением — но JSON без комментариев;
  просто добавить ключ с осмысленным значением, напр. `"127.0.0.1:9090"`, ИЛИ
  оставить пример без него и задокументировать в README/handoff). Не ломать
  существующие ключи.
- **Публичные контракты `proxy.Backend`/`Balancer`** — сигнатуры не менять.
  `breaker.Config` расширяется новым опциональным полем (обратно совместимо: nil =
  прежнее поведение).

## Тест-кейсы (перечень; код пишет исполнитель, все прогоны под `-race`)

### A. Валидация конфига (`internal/config`, table-driven)

Позитивные + негативные кейсы по каждому валидируемому полю. Тестировать через
`Config.Validate()` (без файла) плюс минимум один прогон `Load()` с временным
файлом на диск для сквозной проверки.

1. **Валидный полный конфиг** (эквивалент `config.example.json`) → без ошибки.
2. **`Listen` пустой** → ошибка, сообщение упоминает `listen`.
3. **`Listen` неразбираемый** (напр. `"::::"` / `"host:notaport"`) → ошибка с
   значением.
4. **`Listen` вида `:8080`** (host пуст, порт есть) → валидно.
5. **`Backends` пустой список** → ошибка «no backends».
6. **`Backends` с относительным/невалидным URL** (напр. `"/foo"`, `"://x"`,
   `"not a url"`) → ошибка, упоминает проблемный элемент.
7. **`Backends` все абсолютны** → валидно.
8. **`health_check.interval_seconds` отрицательный** → ошибка. **Ноль** → валидно.
9. **`health_check.timeout_seconds` отрицательный** → ошибка. **Ноль** → валидно.
10. **`breaker.open_timeout_seconds` отрицательный** → ошибка. **Ноль** → валидно.
11. **`retry.max_retries` отрицательный (`-1`)** → **валидно** (`Load()` не
    валидирует retry; нормализация в потребителе). Явно закрепляет Решение 4.
12. **`retry.backoff_base_ms` = 0 и отрицательный** → **валидно** (не валидируется).
13. **`breaker.failure_threshold` = 0 и отрицательный** → **валидно** (не
    валидируется; конструктор нормализует к 1).
14. **`Load()` на несуществующий файл / битый JSON** → ошибка (существующее
    поведение сохранено).
15. **`metrics_listen` omitted** → валидно, поле пусто (метрики выключены).
    (Опционально: если решено валидировать непустой `metrics_listen` как адрес —
    добавить кейс; для MVP достаточно не валидировать пустой и принимать любой
    непустой, а ошибку словить при `ListenAndServe` — исполнителю решить, но не
    усложнять сверх нужного.)

### B. Логирование переходов breaker'а (`internal/breaker`)

Проверять через `OnTransition`-колбэк напрямую (проще и детерминированнее, чем
парсить `slog`-вывод) — колбэк ЕСТЬ механизм, а `slog` — лишь его потребитель в
`proxy`. Дополнительно один тест в `proxy` через `slog` с buffer-handler'ом, чтобы
доказать сквозную интеграцию «переход → лог с backend-меткой».

16. **closed→open по порогу:** колбэк вызван РОВНО один раз с `(closed, open)` при
    достижении `FailureThreshold`; при последующих `Report(false)` в open —
    больше НЕ вызывается (open-ветка `Report` — no-op).
17. **open→half-open:** после истечения таймаута первый `Allow()`, выигравший CAS,
    триггерит колбэк `(open, half-open)` РОВНО один раз; параллельные
    `Allow()`-проигравшие CAS колбэк НЕ триггерят (см. кейс 20).
18. **half-open→closed:** `Report(true)` в half-open → колбэк `(half-open, closed)`
    ровно один раз.
19. **half-open→open:** `Report(false)` в half-open → колбэк `(half-open, open)`
    ровно один раз.
20. **Горячий путь closed без переходов НЕ зовёт колбэк:** серия `Report(true)` и
    `Report(false)` ниже порога в closed → колбэк не вызывается вообще (кроме
    финального перехода при достижении порога). Успешный `Report` в closed —
    никогда не переход.
21. **`OnTransition == nil` безопасно:** breaker с nil-колбэком работает как
    прежде (совместимость; ни один существующий тест Этапа 3 не должен упасть).
22. **`State.String()`** — unit-тест на читаемые имена (closed/open/half-open) и
    поведение на неизвестном значении (не паниковать).
23. **Сквозной slog-тест в `proxy`:** через `slog`-handler в буфер + backend с
    известным URL прогнать closed→open (5xx до порога) и проверить, что в выводе
    есть запись перехода с полем `backend` == URL этого backend'а и `to=open`.

### C. Конкурентный аспект колбэка (`internal/breaker`, `-race`, ОБЯЗАТЕЛЕН)

Хук трогает горячий путь Report/Allow, значит нужен race-тест, доказывающий, что
колбэк не привнёс гонку и не сломал «ровно один пробник».

24. **«Ровно один пробник» сохранён при активном колбэке:** повторить существующий
    конкурентный тест half-open (`TestBreaker_HalfOpen_ExactlyOneTrial`-паттерн из
    SKILL.md) с НЕ-nil `OnTransition`, который атомарно считает вызовы. Под
    `-race`, N=100 горутин, общий `start`-канал. Ассерты: ровно ОДНА горутина
    получила `true` (инвариант Этапа 3 не сломан); колбэк `(open, half-open)`
    вызван РОВНО один раз (переход совершил только победитель CAS), не N раз.
    Прогонять с `-count` при отладке (по SKILL.md).
25. **Stress под `-race`:** N горутин крутят `Allow()`/`Report()` в цикле при
    активном колбэке (колбэк атомарно инкрементирует счётчик) — детектор гонок
    молчит; колбэк не приводит к data race на своих локальных from/to и на
    breaker-состоянии.

### D. Счётчики метрик (`internal/proxy`)

Проверять рост `expvar`-счётчиков в ожидаемых точках. Читать значения через
`expvar.Get(name).(*expvar.Int).Value()` или экспортированный из `export_test.go`
доступ. Учитывать, что `expvar`-счётчики глобальны на пакет — если тесты бегут в
одном процессе, снимать дельту (значение до/после), а не абсолют, чтобы тесты не
зависели от порядка.

26. **`requests_total` растёт** на каждый проксируемый запрос (+1 на запрос).
27. **`errors_total` растёт** на запрос, завершившийся ошибкой клиенту (backend
    всегда 5xx / транспортная ошибка, ретраи исчерпаны) — ровно +1, не по числу
    попыток.
28. **`fast_fail_total` растёт** при отсутствии backend'ов/всех open (сценарий
    как `TestRetry_NoAvailableBackends503`) — +1.
29. **`retries_total` растёт** на число фактических повторов: backend «N ошибок
    затем успех», `MaxRetries >= N`, GET → `retries_total` += N (не N+1: первая
    попытка — не retry).
30. **Успешный запрос НЕ инкрементирует `errors_total`/`fast_fail_total`** —
    негативная проверка, чтобы счётчики не срабатывали ложно.

### E. Совместимость Этапов 1–4

31. **Все существующие тесты `breaker`/`proxy`/`healthcheck`/`config` зелёные** под
    `go test -race ./...`. В частности `TestRetry_MaxRetriesZeroOrNegativeSingleAttempt`
    и regression-дефолты Этапов 2–3 — без изменений (Решение 4).
32. **`config.example.json` по-прежнему загружается и валидируется** (кейс 1
    покрывает; если добавлен `metrics_listen` — пример остаётся валидным).

## Критерий готовности (DoD)

- **Конфиг валидируется:** `config.Load` отвергает пустой/битый `Listen`, пустой
  список backend'ов, невалидные backend-URL и отрицательные
  interval/timeout/open_timeout с понятными сообщениями; ноль этих временных полей
  и любое значение retry/failure_threshold — принимаются (Решения 4, 5). Табличные
  тесты (позитив+негатив по каждому полю) зелёные.
- **Переходы breaker'а видны в логах:** каждый реальный переход
  (closed→open, open→half-open, half-open→closed, half-open→open) порождает ровно
  одну `slog`-запись с backend-меткой; горячий closed-путь без переходов не логирует
  и не платит за колбэк. Доказано колбэк-тестами (B) и сквозным slog-тестом (23).
- **Метрики видны:** при заданном `metrics_listen` второй `http.Server` отдаёт
  `expvar`-счётчики (`/debug/vars`); счётчики растут в ожидаемых точках (D).
- **Конкурентность не сломана:** «ровно один пробник» под `-race` с активным
  колбэком (24); stress под `-race` молчит (25). Порядок atomic-операций Этапа 3
  не изменён.
- **Совместимость:** все тесты Этапов 1–4 зелёные; `TestRetry_MaxRetriesZeroOr
  NegativeSingleAttempt` и regression-дефолты Этапов 2–3 не тронуты.
- `gofmt -l .` пусто, `go vet ./...` и `go test -race ./...` зелёные.
- `internal/breaker` конкурентная модель не тронута (только опциональный хук +
  `State.String()`); архитектура ретрая не переделана (только счётчики поверх);
  JSON-схема существующих полей и `config.example.json`-секции не менялись (только
  добавлено опциональное `metrics_listen`).
